# Project Context

> High-level context for the project: the problem being solved, who it's for, what's in scope, and what constraints apply.

---

## 1. Problem Statement

People want a sensible weekly plan for dinners so they don't have to think about food every day, run to the store at random, or waste money. They have preferences and allergies that should be respected, want roughly the cheapest overall shop without chasing every sale, and are curious about their weekly cost and calorie patterns.

Today this requires juggling a recipe app, a notes app for the shopping list, and mental math about which store to go to — and starting over each week from a blank page.

---

## 2. Vision

**Mise** — an AI-assisted weekly meal planner where the user never faces an empty screen. A coherent week of dinners is always already there; the user shapes it through natural language. A single chat thread spans three views — the weekly **Plan**, a consolidated **Shopping list**, and a multi-week **Reports** view — and the AI can modify both the underlying data (swap a meal, recommend a store) and the presentation (add a column, change a chart shape).

Mise is also a **demonstration** of what a deeply AI-integrated Vaadin business application looks like: chat, grids, charts, and dashboard widgets coordinated by one orchestrator over shared state, rather than a chat bot bolted onto a form.

Concept docs and rough mockups live under [`ai-meal-planner/mise/`](../ai-meal-planner/mise/). See in particular [`concept.md`](../ai-meal-planner/mise/concept.md) for the product vision and [`concept_demo_notes.md`](../ai-meal-planner/mise/concept_demo_notes.md) for what's stubbed and why.

## 3. Users

| Role | Description | Access Scope |
|------|-------------|--------------|
| **Home cook** | The single user of a household. Plans dinners, shops, occasionally hosts. Interacts with Mise on the couch, at the kitchen counter, and standing in a supermarket aisle. | Full access to their household's plan, shopping list, reports, pantry, preferences, and conversation. |
| **Developer / demo presenter** | Engineer cloning the repo to learn the patterns, or presenting the demo on stage. Edits seed YAML files to make AI reasoning visibly change. | Filesystem access to seed data (recipes, stores, personas). No in-app "admin" role. |

In the demo there is **one household and one user** — no authentication, no sharing. Multi-user / multi-household is explicitly out of scope (see §4).

---

## 4. Scope

> High-level capabilities, not detailed features (those go in use cases).

### In Scope

- **Weekly meal plan** for a single household: seven dinner slots, generated by default and editable through natural language.
- **Consolidated shopping list** derived from the plan, the pantry, and store catalogs, grouped by aisle, with store recommendations that weigh price against detour cost.
- **Multi-week reports** with standard cost and nutrition charts, plus AI-driven additions (new queries, new columns, chart-shape changes) that persist across page reloads and JVM restarts via `ViewPreference`.
- **One shared conversation** scoped to the household, spanning all three views, with awareness of the current view but no per-view context reset.
- **Household preferences** (dietary constraints, allergies, hated foods, budget targets, hosting patterns) that persist across weeks.
- **Pantry** items the user already has, subtracted from shopping lists.
- **Inspectability** — the user can ask "why did you change that?" on any AI-driven change.
- **Reversibility** — every AI-driven change to a plan or view can be undone within a session.
- **Insights** — occasional unprompted observations from the AI, presented as advisory and dismissable.
- **Configurable AI model** — the underlying chat model is swappable via configuration; the default is a local OpenAI-compatible endpoint (see §5).
- **Service-oriented backend** — `RecipeCatalog`, `PriceCatalog`, `NutritionEstimator`, etc. sit behind interfaces with file-backed stub implementations for the demo, replaceable without changes to the orchestrator or UI.
- **Persistent state** — plans, conversation history, pantry, and preferences survive app restarts (H2 file-mode database).
- **Responsive UI** — mobile-first; layouts scale cleanly to tablet and desktop. The same orchestrator and capabilities are available at every form factor.

### Out of Scope

- Authentication, multi-user accounts, household sharing.
- Real-time price feeds, retailer integrations, scraped catalogs (static seed data only).
- Medically-accurate or AI-estimated nutrition for user-submitted recipes (`NutritionEstimator` exists as a stub).
- Image generation or photography for meals.
- Multi-language support (English only) and multi-currency (euro only).
- Calendar integration (hosting events, travel days picked up automatically).
- Recipe-to-plan suggestions ("I want to cook this — fit it into my week").
- Real-time inventory integration with specific retailers.
- A "lite" Shopping view without pricing.

## 5. Constraints

- **Vaadin AI orchestrator on Spring AI.** The AI integration uses the Vaadin Flow AI support documented at <https://vaadin.com/docs/next/flow/ai-support>. The orchestrator mediates between services and the UI; it does not own data.
- **Configurable chat model.** The model is swappable via Spring configuration. The demo default is a **local, unlimited-use** OpenAI-compatible endpoint: `Qwen3.6-35B-A3B-UD-Q5_K_XL` at `http://192.168.1.196:8080`. The system must run against any OpenAI-compatible endpoint by changing config alone.
- **Service-oriented architecture.** Domain capabilities (`RecipeCatalog`, `PriceCatalog`, `NutritionEstimator`, plan service, conversation service, etc.) sit behind interfaces. Stub implementations in the demo are backed by seed YAML / JSON files; production implementations can replace them without touching the orchestrator or UI.
- **Bounded AI capabilities.** The AI can only do what the application exposes to it as tools/capabilities. Adding capabilities is a deliberate development act.
- **Persistent state on H2.** Plans, conversation history, pantry, and preferences persist across restarts using H2 in file mode. Seed data is loaded on first run; in-app changes are written back to H2, not to the seed files.
- **Mobile-first responsive UI.** The Plan, Shopping list, Reports, and chat must all work at narrow widths. Layout adapts to screen size; orchestrator behavior does not.
- **Quality bars from the concept** apply as constraints on every feature: AI-driven UI changes reflect in <2s for typical edits (≤5s for multi-constraint reasoning, with progressive chat feedback); the AI never invents prices or macros; every AI change is explainable and reversible; tone is warm, pragmatic, and brief.
- **Demo inspectability.** Editing a seed file (e.g. `demo/data/stores/lidl.yaml`) and restarting the app must visibly change AI reasoning — this is a teaching feature, not an incidental property.

> For technology stack and application structure details, see [`architecture.md`](architecture.md).

## 6. Assumptions

1. The local Qwen endpoint at `http://192.168.1.196:8080` is reachable from the development and demo machines and provides OpenAI-compatible chat completions with tool-calling support sufficient for the orchestrator's tool-use patterns.
2. The seed dataset (recipes, stores, personas, historical plans) is small enough to load into memory at startup and persist into H2 without performance concerns.
3. Demo usage is single-user, low-concurrency. No load-testing, rate-limiting, or horizontal-scaling concerns apply.
4. The default persona ("two adults, omnivore, midweek cooking, ~€90/week, occasional hosting") is the one used unless a developer explicitly switches it.
5. Users interact primarily in English. Currency is euro throughout.
6. Network access to the local model is reliable during demos; degraded-model or offline fallback is not required for the demo.

---

## 7. Risks

- **Model quality.** A local 3B-active-parameter model may produce inconsistent tool-call structure or hallucinate ingredients/prices, undermining the "AI reasons over real data" pitch. *Mitigation:* model is configurable — swap to a larger hosted model for high-stakes demos; structured-output validation in the orchestrator rejects malformed tool calls; the "numerical honesty" rule means the AI must say "I don't have that" rather than guess.
- **Latency.** The 2s / 5s latency bars may be hard to hit against a local model on modest hardware, especially for multi-constraint negotiations. *Mitigation:* progressive feedback in chat; cache plan-level computations; keep tool-call surface area small per turn.
- **Endpoint availability.** The hard-coded local IP `192.168.1.196:8080` is a single point of failure for the default config. *Mitigation:* model and endpoint are config properties, not source-coded; documented fallback to a hosted OpenAI-compatible endpoint.
- **Stubbed data drifting from "feels real."** Static prices and a fixed recipe library can feel canned if the seed dataset is too small or too uniform. *Mitigation:* target ~80 recipes with cuisine and difficulty spread; three stores with meaningfully different price points and detour costs; four weeks of seeded plan history.
- **Orchestrator/UI coupling creep.** It is tempting to let the orchestrator know about specific UI components. *Mitigation:* the architectural principle "orchestrator mediates, does not store" is load-bearing; AI output is structured data the UI applies, not direct UI manipulation.
- **Persistence/seed-data confusion.** If users edit seed YAML expecting changes to take effect, but H2 has already snapshotted the state, the "edit a file and see AI reasoning change" demo moment breaks. *Mitigation:* document the reload behavior clearly; consider a developer flag to re-seed from files on startup.
